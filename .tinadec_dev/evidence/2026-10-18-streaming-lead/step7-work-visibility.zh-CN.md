## 测量：用户抱怨「突然显示」到底是什么

从真实库 5 个 completed run 的时间线量出：

| run | run 开始 → answer.started | 答案窗口 | 静默占比 |
|---|---|---|---|
| 1AD5BA8C | 19.1 s | 8.5 s | **69%** |
| 29A7F645 | 12.7 s | 3.7 s | **77%** |
| 6E36E2E4 | 74.1 s | 11.7 s | **86%** |
| 94FC4AD7 | 36.3 s | 13.4 s | **73%** |
| F3C56554 | 62.8 s | 18.9 s | **77%** |

**69%–86% 的运行时间，界面上什么都没有。**

这不是「落盘慢」，也不是「没接流式」。这是**答案出现之前没有任何东西可看**。

## 流式机制本身是好的（已证）

同一批 run 的正文帧间隔与大小：

```
44362ms  answer.delta  152 bytes
44582ms  answer.delta  268 bytes
44825ms  answer.delta  150 bytes
45052ms  answer.delta  213 bytes
...每 200-300ms 一帧，持续 3.6 秒
```

**这是健康的流式。** 帧间隔均匀、增量真实、`useSmoothText` 还会把每帧再摊平
（模拟验证：261 字符摊到约 600ms 呈现，不是瞬间弹出）。

所以「突然显示」的观感来自**前 36 秒的空白**，不是最后 3 秒的流式。

## 改动

`ConversationTurn.vue`：当一个 run 处于活跃状态但还没有答案文本时，
在答案本该出现的位置渲染一个呼吸中的「正在起草…」占位。

```vue
<p v-else-if="run.live" class="conversation-answer-drafting" role="status">
  {{ t('conversation.reasoning.drafting') }}
</p>
```

三点设计取舍：

1. **位置在答案区，不在活动区**。活动折叠块里已经有「正在思考」，
   但那是 12px 灰字。用户视线落在答案该出现的地方，占位要放在那里。
2. **判据只用 `run.live`**，不看 activity 有没有内容。
   run 刚启动时 entries 为空，而那正是最需要占位的时刻。
3. **复用既有 shimmer 手法**（`background-clip: text` + 线性渐变位移），
   不发明第二套动画语言；`prefers-reduced-motion` 下退化为静态灰字。

## 测试

新增 `ConversationTurn.test.ts` **4/4**：

## 诚实边界

1. **我没有在真实 Electron 里看过这个占位的实际效果。**
   4 个测试证明的是渲染条件与 DOM 存在，不是视觉观感。

2. 占位只解决「看起来在干活」。它不会让用户的等待变短——
   前 36 秒里模型确实在思考/调工具，那段时间没有答案可流。

3. 真正缩短静默需要提高模型首字延迟或减少前置步骤，
   那是另一条优化线，本次没动。
