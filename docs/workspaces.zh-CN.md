# 工作区、侧边栏与源文件夹契约

适用：2026-10-10 工作树。功能与验收进度唯一归属 [APP-HOME-107](development-program/02-modules/app/home/TODO.md#app-home-107)；实现及平台证据见 [实施报告](../.tinadec_dev/reports/2026-10-10-sidebar-workspaces.zh-CN.md)。本文件定义产品行为，不将尚未完成的平台验收写成通过。

## 工作区与自由对话

一个工作区拥有稳定存储作用域、一个或多个源文件夹、一个主文件夹，以及独立的对话和配置。源文件夹是工作材料的位置；作用域是配置与运行事实的归属。两者分开登记。主文件夹可以改变，创建时确定的存储位置保持不变。

自由对话是列表中的普通一项，使用 `user` 作用域，不要求添加源文件夹，也可以和项目工作区一起拖动排序；没有手动顺序时默认排在最前。首次启动没有已恢复的工作区上下文时进入自由对话；不会自动使用列表中第一个项目工作区。

业务请求使用 `X-Tinadec-Storage-Id`，受管 HTTP 请求同时由可信宿主签发。工作区身份与项目配置文件不具备宿主授权效力。业务请求不能直接指定任意数据库连接或目录来读取另一作用域。

## 侧边栏

顶部导航与工作区列表之间显示“工作区”标题。标题控制整组展开、收起；标题的指示器和加号在悬停或键盘聚焦时出现，触发器保留可访问名称与真实 `aria-expanded`。默认整组及所有工作区展开。

工作区整行只控制该工作区对话列表展开、收起，不切换对话、存储作用域或页面布局。行内加号开始对应工作区的新对话；点击子列表才打开已有对话。更多菜单、加号与拖动操作不冒泡触发行折叠。顶部“新聊天”沿用当前上下文，当前为自由对话时继续自由对话。

每个工作区显示当前平面或空间视图中最近五条对话。正在查看的旧对话额外保留，因此最多可见六条。“展开显示”显示当前分类全部对话，“收起显示”恢复近期列表。长列表使用侧边栏统一滚动，工作区内部不增加滚动容器。

自由对话与项目工作区共享同一个手动顺序。新工作区插入现有自由对话项之后，位置固定后不再随刷新变化；支持整行拖动（落点上半区放到目标前、下半区放到目标后）以及菜单和键盘的上移、下移。运行消息、会话刷新与最后更新时间不改变该顺序。整体折叠、各工作区折叠、显示全部与顺序按稳定 `storage_id::project_id` 保存，不能仅用目录路径或名称作为状态键。

每个工作区分别显示加载中、暂无对话或加载失败；一个工作区的请求失败不阻止其他列表，重试只影响对应工作区。列表状态属于本机偏好，不改变工作区 TOML、权限或会话事实。

## 创建、打开与编辑

标题加号、发送框入口与打开项目入口共用 `WorkspaceEditorDialog`，复用现有 shadcn-vue/Reka 组件、材质与设计令牌。

本轮支持本机已有目录，至少一个、最多三十二个，拒绝文件系统根目录与重复目录。目录拥有稳定 ID；Windows 按规范化路径忽略大小写去重，Linux/macOS 按平台路径规则处理。目录选择 IPC 返回路径数组，不创建目录或初始化存储。

窗口包含源文件夹、主要标记、名称、图标和颜色。首个源文件夹自动设为主要，名称取主文件夹名；用户编辑名称后，更换主要目录不再覆盖该名称。其他目录可“设为主要”或移除；移除主目录前须先选择另一个，最后一个不能移除。移除的是引用，真实目录和文件保留。

选择目录与取消窗口不初始化存储。确认创建后只提交一次请求，成功后展开新工作区并进入其新对话上下文。遇到已有宿主登记或完整存储时，先显示已有工作区信息，由明确的“打开已有工作区”动作进入，保留原配置。源目录缺失、损坏配置、文件冲突、链接越界或初始化失败均显示原因，不静默覆盖或重建。

更多菜单的“编辑工作区”使用同一窗口。保存提交原配置摘要；无 `If-Match` 返回 428，摘要已变化返回 412。冲突保留原文件，用户重新读取后编辑。创建、预览和显式打开沿用同一作用域身份，不能因重复点击登记多份工作区。

归档、回收站、取消登记、删除会话与删除整个工作区存储继续是独立动作；编辑源文件夹列表不触发任何这些动作。

## 工作空间卡片

右侧功能面板的 `workspace` 卡片是工作空间资源的第二个入口，不是第二套授权系统。它读写本文档描述的 `workspace.roots[]` 与 `workspace.files[]`，提交走同一个 `PUT /api/v1/storage/scopes/{id}/workspace`（前端 `api.saveWorkspace`），因此摘要条件、原子替换、宿主授权发布与可重建投影刷新都与「编辑工作区」窗口一致；不存在只为卡片新增的 Core 保存端点。卡片是单例：一个工作区只有一份资源列表，两张卡等于给同一份 `project.toml` 开两个编辑器，后保存的那个会覆盖前一个的编辑。

首页功能网格与页签「+」菜单同时出现入口，两者同源于 `featureCatalog.ts`；预设页签数组刻意不含它，与文档查看器、代码编辑器一致——改预设只影响全新安装与「重置布局」，却会让既有用户的页签排列无缘无故变化。

列表规则与窗口相同：至少一个、最多三十二个，拒绝重复目录与文件系统根目录，主文件夹与最后一个不能移除；移除的只是引用，真实目录与文件保留。重复目录、个数上限与这两条移除限制在卡片里当场给出可读错误；文件系统根目录与目录是否真实存在由 Core 的 `WorkspaceDefinition.Validate` 拒绝并把原因带回界面，前端不另写一套判定。保存时若 `project.toml` 已在别处变更，Core 返回 412，卡片以错误通知呈现原因；控制器把失败收进通知而不是抛给卡片，因此卡片另有一条「列表没有变化」的状态行，带「载入最新配置」按钮重新读取项目与摘要——它不重试同一次写入，也不静默覆盖。

**加源文件夹或精确文件只放宽资源边界，不放宽审批门。** 目录集合决定一棵目录树是否可达；单文件授权只决定这一条精确路径是否可达。写操作是否逐次审批仍由会话冻结的权限模式决定，只有冻结值为 `full-access` 的运行免逐次审批（`ToolApprovalCoordinator` 只对这一种值放行，`ToolApprovalPolicy` 另有独立开关）。卡片因此只陈述当前模式与它的后果，并把切换入口指向发送框的权限菜单，不提供「为本工作区免审批」的开关——那等于让一个文件管理动作改写运行安全策略。

**改动只对新运行生效。** 目录与精确文件集合在准入时冻结，并共同参与工具进程的隔离键（`TinadecToolsProcessManager` 的 `processKey` 含两组资源摘要），所以正在执行的任务、已完成运行与既有终端仍用旧集合，下一轮对话才看见新资源。卡片上的保存成功不等于「当前回答已经能读这个文件」。

拖入有三种意图，**不能合并**：**文件夹就地成为源文件夹**（追加 `roots`，递归授权整棵目录）；**文件就地绑定原文件**（追加 `files`，只授权这个精确路径，不扩展到父目录的兄弟文件）；**复制进工作空间**是卡片上的显式按钮，复制后由主文件夹的目录授权覆盖。把一张截图拖进卡片不会再先复制，也不会为了读取它而授权整个下载目录。

“附到当前对话”复用发送框的待发附件状态，不创建会话。没有选中会话时文件先留在本地暂存；发送动作创建会话后才上传，并把 `origin=workspace` 与 `source_path` 一起交给 Core。附件字节是上传时的不可变副本，文件授权则仍指向原路径；两者是不同事实，不能互相冒充。

复制由主进程 IPC 完成：渲染层拿不到拖入文件的真实路径（`File.path` 早已移除），需在 drop 事件内经 `pathForFile` 解析；解析不到的条目按名称报为未复制，**不静默丢弃**——空结果会被读成「没有要复制的」。工具层拒绝一切经过符号链接的路径（`TinadecTools/Tools/FileRW/FileToolRuntime.cs` 的 `EnsureNoLinkTraversal`），所以主进程也拒绝链接而不是跟随：复制进来的链接文件智能体永远读不到。IPC 只接受可信主页面、只接受已存在的绝对目标目录、只创建新文件且同名项按存在报告为跳过而从不覆盖，并有两条上限：单次最多 200 个文件、单文件最大 64 MiB（超出按 `too_many` / `too_large` 逐项报告，同批次的其余文件照常复制）。逐项返回 `imported`（名称、落点、字节数）与 `skipped`（原因用稳定代码，措辞归渲染层）。

文件夹与文件的区分只能靠 `DataTransferItem.webkitGetAsEntry()` 的 `isDirectory`——它是 drop 里唯一能在解析路径前判断类型的手段；浏览器不提供 API 枚举目录内容，所以拖入的文件夹是**整体加为源文件夹**，不会逐文件复制。

### 精确文件与附件曝光

精确文件授权保存在 `project.toml`。它与目录使用不同表，避免把文件误当成可递归的父目录：

```toml
[[workspace.files]]
id = "brand-guide"
path = "../shared/brand-guide.pdf"
```

宿主登记同时保存 `authorized_files` 与 `historical_files`。项目文件自行增加 `workspace.files[]` 而没有对应宿主授权会得到 `workspace_authorization_required`，与目录篡改同一失败方式。单文件快照由独立 provider 捕获和恢复，不会把父目录中的其他文件带进审批或回滚。

“给 Agent 看过的东西”列表来自项目附件曝光端点 `GET /api/v1/projects/{id}/exposures`。每个附件记录 `origin`（`composer` 或 `workspace`）、`project_id`、可选 `source_path`、`delivered_to_model`、`delivered_run_id` 与 `delivered_at`。普通对话附件也会带上项目归属，因此项目列表能统一回答“哪些文件进入过这个项目的对话”；工作空间来源还额外保留原路径。

**送达不是上传。** 上传只创建不可变字节副本；只有解析出的模型明确支持图片输入且该图片实际作为 `DataContent` 进入该 run 的模型消息后，Core 才记录送达事实。能力关闭、协议不支持、单图超限、张数超限或总量超限都会在模型提示中写明哪张图片没有送达以及原因，绝不静默消失。

## 存储位置与 TOML

默认在**创建时的主文件夹**下初始化一份 `.tinadec`；附加文件夹不初始化自己的存储。无法写入时沿用明确外部模式 `~/.tinadec/projects/<storage_id>/`，界面与诊断显示实际落点，重启可恢复。主动选择的外部根也不自动搬迁旧数据。

主文件夹改变后，默认命令目录、相对路径起点、新终端与 Git 面板使用新的主目录。现有终端、运行、审批、队列与 SSE 保持各自已绑定的作用域与目录。切换发送框中的工作区进入该工作区的新对话上下文；已有会话归属只通过现有显式迁移动作修改。

权威文件为实际存储根的 `project.toml`。示例中的 `app`、`library` 是稳定目录 ID；路径相对于创建时的存储锚点源目录解析，跨盘时可以保存绝对路径。

```toml
schema_version = 1
project_id = "b108b078-9669-44f1-b839-72e1e2878f18"
backend = "sqlite"

[workspace]
name = "TinadecOffice"
primary_root_id = "app"
icon = "code"
color = "blue"

[[workspace.roots]]
id = "app"
path = "."

[[workspace.roots]]
id = "library"
path = "../TinadecUI"

[[workspace.files]]
id = "brand-guide"
path = "../shared/brand-guide.pdf"
```

目录 ID 使用 1–64 个字母、数字、下划线或连字符，工作区名称为 1–128 个字符。图标和颜色来自共享有限选项，界面与后端使用同一契约。旧单目录配置读取为一个 `primary` 源目录，读取本身不改写文件；显式编辑时才保存扩展信息。

保存依次获取作用域编辑门和 `state/.workspace-write.lock` 文件租约，校验摘要与授权，写入同目录临时文件、落盘，再次核对摘要后原子替换。未修改字段与注释保留。成功发布宿主授权与项目投影；正常失败、取消清理临时文件。未知外部编辑不覆盖；项目文件自行增加目录会得到 `workspace_authorization_required`，需要可信宿主明确授权。

源文件夹当前授权与历史授权保存在用户根的宿主登记中。稳定项目身份与本机宿主登记分开；项目移动可重新绑定，复制项目产生独立宿主实例。不能使用项目文件里的身份扩大读写权。

选择 PostgreSQL 时，每个工作区使用独立 schema，EF 与向量连接固定同一作用域，业务连接不回退到公共 schema。新安装的 pgvector 扩展放在数据库公共 schema；已有扩展按其实际命名空间引用，不自动迁移。数据库时间精度与 TOML 不同时，历史版本按数据库保存精度比较，源文件保持原字节，其他不可变字段仍严格校验。

若既有数据库把公共扩展安装在某个工作区 schema 内，删除该工作区存储的预览和执行均明确拒绝，要求数据库管理员先处理扩展归属，避免级联删除破坏其他工作区。此保护不自动移动扩展或删除既有数据。

## 运行与工具

新运行冻结完整源目录集合、精确文件集合、目录/文件 ID、主目录、存储作用域与写权限。后续工作区编辑只影响新运行。工具进程按作用域、冻结资源集合与存储写策略隔离，不能切换一个全局“当前项目”连接。

文件读写、搜索、Shell 和 Git 使用全部已授权源目录；文件工具还可以命中精确文件授权，但只对其中的原路径本身放行。缺省路径以冻结主目录为起点，显式命令目录可位于其他源目录。模型参数不能自行添加授权目录或文件，Windows 私有 runner 的启动资源集合由可信上级进程传入。Core 创建的受管理 worktree 使用独立的宿主绑定。

搜索结果与工作区快照使用“目录 ID＋相对路径”，例如 `app/src/main.ts` 与 `library/src/main.ts`，两份同名文件不会混淆。快照保存逐目录状态与内容摘要；恢复核对历史宿主授权及当前内容摘要。已移除源目录的历史引用保留，但不会变成新运行的可写目录。

默认允许源码以及该工作区 `config/`、`skills/`；`data/`、运行状态、日志、缓存等存储内容受保护。整个存储树写权限仍须可信宿主显式授予并冻结。文件工具的拒绝结果、真实 OS 沙箱与进程启动保证分层验收，不以单元测试替代系统权限证据。

## 用户动作与写入

| 用户动作 | 文件或事实变化 | 条件 |
| --- | --- | --- |
| 展开、收起、显示全部、排序 | 本机 `tinadec.sidebar.workspaces.v1` | 不改变当前上下文与 TOML |
| 打开已有会话或进入新对话上下文 | 本机 `tinadec.workspace.context.v1`；已有会话继续按原作用域读取 | 新对话上下文本身不创建会话运行事实 |
| 选择目录、查看已有工作区、取消窗口 | 无存储初始化 | IPC 与预览只读取 |
| 确认创建 | 主目录 `.tinadec/project.toml`、模块配置、作用域数据库与用户宿主登记 | 仅一个存储根；外部模式显示实际位置 |
| 打开已有工作区 | 本机登记和挂载状态 | 原文件不覆盖 |
| 编辑工作区 | 原存储根 `project.toml`、宿主目录授权与可重建项目投影 | 摘要条件保存，原子替换 |
| 更换主要目录 | 同上 | 原存储位置不变，旧运行与终端不改绑 |
| 移除源目录引用 | 同上 | 不删除真实目录；主目录与最后一项有约束 |
| 工作空间卡片里加/减源文件夹、更换主文件夹 | 同上（同一条保存路径） | 与「编辑工作区」同一契约；改动只对新运行生效 |
| 工作空间卡片里绑定/解绑原文件 | 原存储根 `project.toml` 与宿主 `authorized_files` | 只授权精确路径，不推导父目录；改动只对新运行生效 |
| 工作空间卡片里“复制进工作空间” | 主文件夹里的新文件 | 只创建新文件，重名跳过不覆盖；复制后才由目录授权覆盖 |
| 工作空间卡片里“附到当前对话” | 作曲器待发附件；发送后成为带 workspace 来源的会话附件 | 不创建会话；附件字节与文件授权仍是两项事实 |
| 对话附件上传/绑定/送达 | `message_attachments` 的来源与送达事实 | 只有真实作为多模态部件送入模型后才翻转 delivered |
| 发送并运行 | 来源作用域 `data/`、事件、快照及诊断日志 | 新运行冻结目录与配置 |
| 快照恢复 | 快照中指定目录 ID 的真实文件 | 历史授权、哈希及恢复确认流程 |

本机 UI 键不构成权限或配置权威。所有存储分类、日志预算、密钥与清理操作继续遵守 [Core 产品定义](tinadec-core-product-definition.zh-CN.md) §21。产品 `.tinadec`、开发资料 `.tinadec_dev` 与开发工具适配目录严格分开。
